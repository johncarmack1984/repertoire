# Build a review lens

A lens is one maintainer's review, written down from evidence and run before they run it. The bar is merge on sight: when a lensed PR opens, the reviewer finds nothing left to say that the lens did not say first. Review habits are the source, not the contributing guide: the guide is aspirational, the merged PRs and the comments on them are what actually passes.

## Decide first

- **Repo and reviewer scope.** `OWNER/REPO`. One repo per lens; a monorepo with separate owners per directory gets a routing section, not a second lens.
- **Where it lives.** `<notes>/.claude/skills/<name>-lens/SKILL.md` with the evidence beside it at `<notes>/.claude/lens-evidence/<repo>.md`, where `<notes>` is wherever you keep context for that org (a folder beside the clone, or the clone's own gitignored `.claude/`). Symlink the skill into the personal skills directory so it loads from any repo.
- **Your login.** The miner leaves you out of the ranking and reports what your own PRs got.
- **Existing lenses.** If one exists for this repo, refine it (see `reference/refine.md`); a second file for the same reviewer splits the evidence.

## Steps

1. **Mine.** Run `python3 {SKILL_DIR}/scripts/mine_reviews.py OWNER/REPO --me <login> --out <notes>/.claude/lens-evidence/mining/<repo>` (defaults: PRs from the last three years capped at 1,000, the 500 newest inline comments, weights halving every 180 days, four merged outside-author PRs held out). Read-only; it posts nothing. Read `summary.md` in full: the ranking says who reviews now, the arc says who used to, "What outside authors get" is the bar you will be measured against, and "Suggested lens shape" names person versus team. Done when you can say who the gatekeeper is, who merges, and how long an outside PR of each size waits.
2. **Read the environment before the people.** `CONTRIBUTING.md`, the PR template, `CODEOWNERS`, the AI policy if any, the review-bot workflows under `.github/workflows/`, a tracked `CLAUDE.md` or `AGENTS.md`, the merge mode (squash means the body becomes the commit message), and the commands CI actually runs (its workflow files, the justfile, `package.json`). Note where the canonical forge or discussion lives if it is not GitHub (a Gitea mirror, a Trac, a mailing list, a Slack channel), and read that too. Done when the verification commands for step 4 of the lens are copied from CI, not guessed.
3. **Read the corpus, all of it.** `raw/<login>.md` for each top reviewer, newest first, then `raw/declined.md`; `raw/backtest.md` waits for step 6. While reading, cluster: each recurring comment becomes one rule, each closed-unmerged reason becomes a "what gets a no" line, each question they ask before approving (the why, the breaking-change case, the platform witness, the test that fails without the fix) becomes something the lens pre-answers in the PR body. Record the register and the cycle as facts: comment length, suggestion commits, approve-with-caveats, minutes or days to first comment, what a self-close or a nudge reads as. Done when every comment in the corpus is either under a rule, under a cycle fact, or dismissed in writing as a one-off.
4. **Write the evidence file** from `reference/evidence-template.md`: mining line, cast with real names and roles, verbatim quotes numbered per reviewer with PR number and date, what passes, what gets declined, three or more outside-contributor timelines (opened, first reply, asks, merge or close), process and climate. Done when every rule you are about to write can point at a numbered quote here.
5. **Write the lens** from `reference/lens-template.md`. Steps first (scope the diff against the upstream base, strip, apply every rule to every hunk, verify with the repo's real commands, fact-check the body on every push, report one line per ruling), flat rules second, gotchas last, in one file. A rule has a bold lead that states what passes, in the positive, and evidence in parentheses: the reviewer's words verbatim with PR number and date. Two quotes make a rule; one quote is a candidate and says so. Name the lens for the person when one reviewer holds half or more of recent weight, for the repo when it is a team; two strong reviewers get two lenses with a stated order and one named owner of the PR body. Load `/writing-for-agents` before writing. Done when every rule has evidence, every step has a completion criterion, and the description carries its triggers.
6. **Back-test.** For each held-out PR in `raw/backtest.md`: get the diff, run the lens's rules over it as if it were yours, write the rulings down, then open the answer key. Every comment the reviewer made that the lens missed becomes a rule; every ruling the reviewer never made is your taste, not theirs, and gets cut. Record hits over comments in the evidence file. Done when the last held-out PR adds no new rule.
7. **Wire it.** Symlink into the personal skills directory; add the one-line pointer wherever that org's people facts live ("their review rules are the `/<name>-lens` skill: run it before any PR opens or pushes, and when their comments arrive"); add the convention line to the repo's own context file. Done when invoking the lens by name from the clone loads it.

## Refine in use

Every review round is training data, and the lens is the only place the lesson lands. When comments arrive, when a maintainer edits your text before merging, when two reviewers on one repo disagree, and before every push, follow `reference/refine.md`.
